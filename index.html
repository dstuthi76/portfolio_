LakeWatch — data quality and observability platform

LatentView Analytics, in production

A full data quality platform for an ERP lakehouse: a PySpark engine that validates every incoming batch against versioned rules, and a web application where data stewards define those rules without writing code. It governs vendor, item and customer master data arriving from SAP, Great Plains and SalesPad.

Execution engine

  • 19 condition types, including referential checks against governed lookup tables
  • Rule versioning, so a failed record traces to the exact rule that caught it
  • Enforcement actions separating blocking failures from audit-only ones
  • Incremental batch selection by hash-key anti-join instead of full rescans
  • Clean and failed records split by row stamp, with a requeue job that revalidates fixes

Management application

  • Flask and React app deployed as a Databricks App on Unity Catalog
  • Data-type-aware rule builder driven by live catalog metadata
  • LLM-backed rule recommendations from column profiles
  • Approval workflow, rule groups and email alerting through Microsoft Graph

Design and governance

  • 11 config and audit tables — rules, requests, metrics, logs, bad records, alerts
  • Rule taxonomy with exact JSON criteria formats per condition type
  • Field-level data dictionaries mapping ERP fields to rule categories
  • 25-page design document covering schema, lifecycle and deployment

Lakehouse observability suite

LatentView Analytics, five monitoring modules

Five modules built on Unity Catalog system tables. Each one detects its own class of problem, alerts the people who own it, and reports into a dashboard — so cost, query performance, schema drift, SLA breaches and access anomalies are all visible in the same place.

Cost monitoring and anomaly detection

DBU and USD cost attributed by job, cluster, warehouse and SKU from billing usage joined to list prices, with z-score outlier detection per cost series and a dashboard of month-over-month spend, top computes and 60-day averages.

Query observability and optimization

Composite scoring ranks business-critical and poorly performing queries on frequency, duration, rows read and bytes scanned; an LLM returns rewrite and indexing recommendations for the worst offenders, attributed to whoever ran them.

Schema observability and downstream alerts

Schema changes detected from table history, including multi-step data type changes, recorded in a versioned registry, mapped to downstream tables, notebooks, jobs, queries and dashboards through lineage APIs, and alerted to their owners — with rollback scripts per version.

SLA and volume spike monitoring

Config-driven SLA thresholds checked against job run history with breach logging, and ingestion volume compared to per-table baselines so a spike is flagged rather than discovered later.

Security and privacy monitoring

A 30-day access audit categorising failures, authentication methods and action types; dynamic tagging and masking of sensitive columns; permission auditing against least privilege; and Isolation Forest anomaly detection over nine per-user behaviour features including failure ratio, off-hours access and error counts.

llm-toolkit — eight tools for running LLM apps in production

Open source, MIT licensed

A monorepo of eight independently installable Python packages, each aimed at one failure mode that only appears once an LLM application is actually running: agent tracing, context pruning, model routing, structured-output reliability, privacy-preserving RAG and prompt regression testing. Every package ships an offline implementation of anything that would normally need a paid API, so all 58 tests run with no keys and no network. Switching to a real provider is one constructor argument.

ResQNet — offline-first flood response and parametric relief

Open source

A disaster-response platform for the case where the network is the first thing to fail. An SOS raised on a phone with no signal hops device to device until one of them reaches the internet; a control room ranks what arrives and explains the ranking; relief money is released by a contract that reads satellite data instead of waiting on paperwork.

Mesh and trust

  • Android app relaying SOS packets phone to phone over Bluetooth and Wi-Fi Direct
  • Every packet signed with Ed25519, so a relayed message can’t be forged in transit
  • Rescue status travels back down the same mesh to the phone that raised it

Triage

  • 276 messy messages in Telugu, Tamil, Hindi, Hinglish and English become ~64 ranked cases
  • Every case shows why it ranks where it does, rather than emitting a bare score
  • Gemini when a key is present, rule-based extraction when not — the demo runs offline

Relief payouts

  • Sentinel-1 radar change detection in Google Earth Engine gives hours flooded per zone
  • Solidity contract paying only at 48 hours flooded and two of three NGO confirmations
  • Only a salted hash and zone go on-chain; enrolment and SOS patterns checked for fraud
