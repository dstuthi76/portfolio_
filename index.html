About

Data engineer working where the lakehouse meets governance — and increasingly, where governance meets machine learning.

Most of my work starts with a question somebody can’t answer: is this vendor record complete, which rule failed last night, which model version is actually serving. Answering those properly means building the plumbing — config-driven rules, audit tables, lineage, alerting — rather than one more ad-hoc notebook.

At LatentView Analytics I work in an Azure Databricks Unity Catalog environment on a medallion architecture, across ERP master data from SAP, Great Plains and SalesPad. I built LakeWatch end to end: a PySpark execution engine with 19 condition types, rule versioning and enforcement actions, plus a Flask and React application where data stewards define and approve those rules themselves.

Alongside it I built an MLOps model registration framework on MLflow and Unity Catalog — config-driven per use case, with champion/challenger promotion and monitoring — and applied it to supplier-delay and fulfilment-risk use cases.

The AI side has moved from side interest to a working toolkit: I’ve published eight small Python packages for the problems that show up once LLM applications actually run — agent tracing, context pruning, model routing, structured-output reliability, privacy-preserving RAG and prompt regression testing. All of them run offline with no API keys, so the logic can be tested rather than taken on trust.

Beyond Databricks I work with Snowflake and dbt, and with GCP on civic and data projects. I build at hackathons when the chance comes up — most recently a plant operations copilot for the AI Builder Hackathon 2026 — and I write about model serving architecture for the LatentView engineering blog.

LakeWatch — data quality and observability platform

LatentView Analytics · production

A full data quality platform for an ERP lakehouse: a PySpark execution engine that validates every incoming batch against versioned rules, and a web application where data stewards define those rules without writing code. It governs vendor, item and customer master data flowing in from SAP, Great Plains and SalesPad.

Execution engine

  • 19 condition types, including referential checks against governed lookup tables
  • Rule versioning so a failed record can be traced to the exact rule that caught it
  • Enforcement actions separating blocking failures from audit-only ones
  • Incremental batch selection by hash-key anti-join instead of full rescans
  • Clean and failed records split by row stamp, with a requeue job that revalidates fixes

Management application

  • Flask and React app deployed as a Databricks App on Unity Catalog
  • Data-type-aware rule builder driven by live catalog metadata
  • LLM-backed rule recommendations from column profiles
  • Approval workflow, rule groups and email alerting via Microsoft Graph

Design and governance

  • 11 config and audit tables — rules, requests, metrics, logs, bad records, alerts
  • Rule taxonomy with exact JSON criteria formats per condition type
  • Field-level data dictionaries mapping ERP fields to rule categories
  • 25-page design document covering schema, lifecycle and deployment

llm-toolkit — eight tools for running LLM apps in production

Open source · MIT · github.com/dstuthi76/llm-toolkit

A monorepo of eight independently installable Python packages, each aimed at one failure mode that only appears once an LLM application is actually running. Every package ships an offline implementation of anything that would normally need a paid API, so the full suite — 58 tests — runs with no keys and no network. The swap to a real provider is a single constructor argument.

Observability and quality

  • tracewright — pinpoints which step in a long agent run caused the failure
  • agentlint — detects loops, drift and silent give-ups in multi-agent conversations
  • promptcheck — regression testing so prompt edits can’t silently break behaviour

Cost and correctness

  • modelrouter — routes trivial queries away from the expensive model
  • reliably — catches structured output that parses but is wrong, and retries informed
  • contextprune — trims RAG context instead of assuming more is better

Evaluation and privacy

  • finetune_eval — surfaces per-example regressions that aggregate accuracy hides
  • privacyrag — redaction plus an audit trail for RAG over sensitive documents
  • Each package: own pyproject.toml, tests, README and a runnable example
